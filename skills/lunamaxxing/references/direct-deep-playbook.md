# DIRECT-DEEP Playbook

Use this playbook when a substantial task runs DIRECT, especially when its natural DELEGATED or FANOUT topology is blocked because Luna xhigh cannot be verified. Main remains the only worker and writer. Preserve the requested outcome and depth.

## Core rule

**No delegation does not mean reduced work.** Do not compress a large product task into a quick pass, stop after scaffolding, or silently drop acceptance criteria because child capability is unavailable.

## Execution sequence

1. **Define the finish line** — extract the requested outcome, user-visible behaviors, constraints, and decisive validation.
2. **Inspect before designing** — read applicable instructions and existing architecture, assets, conventions, tests, and runtime paths.
3. **Create bounded milestones** — order coherent stages with observable completion conditions. Keep only the current milestone active.
4. **Prove the core path early** — build or validate a minimal vertical slice before expanding breadth.
5. **Implement milestone by milestone** — complete integration and nearby error paths; do not leave disconnected scaffolding.
6. **Validate proportionally** — run targeted checks after each risky milestone and end-to-end checks for the finished outcome. For interactive products such as local web games, exercise the real runtime and user flow when tools permit.
7. **Perform a fresh final review** — inspect the resulting diff or artifact against the original acceptance criteria, then fix material gaps before reporting.

## Sequential evidence lanes

When the natural topology was DELEGATED or FANOUT, Main processes the useful lanes sequentially instead of discarding them. Typical lanes include:

- architecture and integration boundaries;
- runtime behavior and state flow;
- user experience, assets, and interaction quality;
- tests, failure handling, and regression surface.

Use only lanes that can change the result. Record short evidence notes between milestones so later implementation does not overwrite earlier conclusions.

## Iteration discipline

- Continue while an acceptance criterion is unmet, validation fails, or a material regression remains.
- Re-plan locally when evidence invalidates a milestone; do not restart the entire task without cause.
- Prefer working software or inspected artifacts over speculative completeness claims.
- Report runtime limitations separately from product completeness.
